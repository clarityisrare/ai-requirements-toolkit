## Purpose

Use this pattern when a structured AI prompt is itself the requirement — the
deliverable is generated by a model from a prompt, and the prompt, together with its
context, constraints, and success criteria, is what the team reviews, versions, and
signs off in place of a traditional specification.

A prompt can read as clear while hiding ungrounded assumptions, an unnamed data
source, or an unstated success bar. Treat it like any other requirement: traceable,
testable, and human-approved, with each element marked source-supported, inferred, or
missing evidence.

---

## Generic Requirement

The system shall treat each AI prompt used to produce a business deliverable as a
versioned, reviewable requirement that carries its context, constraints, expected
output, success criteria, and a recorded human approval.

---

## Example Requirement

The system shall generate the monthly compliance summary from an approved,
version-controlled prompt whose data sources and success criteria are recorded, and
shall require a named reviewer to approve the output before it is used.

---

## Core Requirement Fields

| Field | Description |
|---|---|
| Objective | What the prompt-driven task must achieve |
| Business Goal | Why the output matters |
| Stakeholders | Who requests, reviews, and consumes the output |
| Constraints | Allowed data sources, tone, format, length, exclusions |
| Prompt Text | The exact prompt, stored and versioned |
| Model & Settings | Which model, effort or temperature, and tools are available |
| Expected Output | The shape and format of a correct result |
| Success Criteria | How a good output is recognized, measurable where possible |
| Grounding | Which claims must be source-supported and which may be inferred |
| Validation | How the output is checked before use |
| Human Approval | Who signs off, and whether approval is required before use |
| Versioning | How prompt changes are tracked and rolled back |

## Example Functional Requirements

### FR-001: Store the Prompt as an Artifact

The system shall store each production prompt as a versioned artifact with an owner
and a change history.

---

### FR-002: Record Context and Constraints

The system shall record the objective, allowed data sources, constraints, and success
criteria alongside each prompt.

---

### FR-003: Ground the Output

The system shall mark each element of the output as source-supported, inferred, or
missing evidence.

---

### FR-004: Require Human Approval

The system shall require a named reviewer to approve the output before it is used for a
business decision.

---

### FR-005: Validate Before Use

The system shall run the defined validation checks on the output and block use until
they pass.

---

### FR-006: Track Prompt Changes

The system shall record every change to a production prompt and allow reverting to a
previous version.

---

## Acceptance Criteria

### AC-01: Prompt Versioned

Given a prompt is used in production

When a user changes it

Then the system shall record the new version with author and timestamp and keep the
previous version.

---

### AC-02: Grounded Output

Given the model produces an output

When a reviewer opens it for review

Then the system shall label each claim as source-supported, inferred, or missing
evidence.

---

### AC-03: Approval Gate

Given an output has not been approved

When a user attempts to use it for a decision

Then the system shall block the use until a named reviewer approves it.

---

### AC-04: Failed Validation

Given the output fails a validation check

When the result returns

Then the system shall mark the output not ready and record the reason.

---

### AC-05: Revert

Given a prompt change degrades output quality

When a reviewer reverts to a prior version

Then the system shall restore that version and record the revert.

---

## Non-Functional Considerations

- Prompts that drive business outputs should be stored and access-controlled like
  source code.
- The model, its version, and its settings should be recorded, since the same prompt
  can yield different results across models.
- Outputs should be reproducible enough to audit — record the prompt version, model,
  and inputs used.
- Sensitive data placed in a prompt should follow the same privacy rules as any other
  system input.
- Review effort should scale with the risk of the decision the output supports.
- A prompt whose output cannot be grounded in a source should be flagged, not silently
  trusted.

## AI Review Prompt

```text
Act as a Senior Requirements Engineer reviewing an AI prompt used as a requirement.

Review the following prompt-as-requirement.

Check for:

1. Clear objective and business goal
2. Named stakeholders
3. Explicit constraints and allowed data sources
4. Expected output shape and format
5. Measurable success criteria
6. Grounding: which claims must be source-supported
7. Validation method before the output is used
8. Human approval gate and its owner
9. Model and settings recorded
10. Versioning and rollback
11. Privacy of data placed in the prompt
12. Ambiguous wording

Return findings as a markdown table with:

- Issue
- Risk
- Suggested improvement
- Severity
```
